# Tasks

Conventions used below:
- `<base>` is the commit this change starts from; task 1.1 records it before any edit.
- `<scratch>` is a folder outside the repository. Baselines, reports, screenshots and the `<base>` worktree go there, never into the repository.
- `$PW` stands for `npx -y -p playwright@1.63.0 -p tsx@4.23.15 tsx`. Browsers run one at a time. WebGL runs on the GPU (`--use-angle=metal --enable-gpu --ignore-gpu-blocklist`), the renderer the loops were recorded with.
- `<dev>` and `<dev-4d>` are development servers of the working tree: `npx vite -c sites/playground/vite.config.ts --port <p> --strictPort` and `npx vite -c sites/4d-os/vite.config.ts --port <q> --strictPort` (4D.OS is served at `/`, so the harness takes it through `--os <dev-4d>`). `<dev-base>` and `<dev-base-4d>` are the same two servers started from the `<base>` worktree of task 1.2. They write nothing to `dist/`. Stop the servers you start.
- `<url>` is a local server of a production build: `rm -rf dist && npm run build && cp deploy/_redirects deploy/.assetsignore dist/`, then `npx wrangler dev -c deploy/wrangler.jsonc` with a free port on the loopback interface (the flags are in the header comment of `tools/capture-loops.ts`). `<url-base>` is the same for a build of `<base>`, made inside its worktree.
- **Where proofs run (design D16).** Implementers (groups 1 to 7) work and self-check on `<dev>` and `<dev-base>` only. They never run `npm run build` in the main checkout, never write its `dist/`, and never serve `<url>` (the harness's build of `<base>` inside its own worktree, task 1.2, is the one exception): seven owners share one working tree, and a build type-checks everyone's half-written files and clobbers `dist/`. Only the integrator (group 8) builds `<url>`, runs every proof on it, and sends each failure back to the file's owner. Checks that depend on production bundling (load times under throttling, transfer budgets, built heads) are proven only on `<url>`.
- **Hand-over.** An owner hands over when its group's closing task passes and `npm run typecheck` reports no error in its own files (errors in files another owner is still editing are listed in the report; group 8 requires a clean run). The hand-over report holds the measured figures, the `DESIGN.md` note the group's closing task names, and any finding in a file the owner does not own. Implementers do not edit `tasks.md`, `LICENSES.md` or `docs/design/DESIGN.md`; the integrator ticks tasks, merges notes and records results in `verification.md`.

Owners (design D19): **harness** (group 1), **museum** (2), **bloomscope** (3), **game-center** (4), **wind-up-empire** (5), **engine-window+worlds-abc** (6), **engine-pack+worlds-de+launcher** (7), and **integration** (groups 8, 9 and 10). Each owner edits only its own files; a finding in another owner's file goes back to that owner.

Order: group 1 comes first and is complete before any other group starts, because every page module implements its `PageCheck` interface, every owner's desktop self-check compares against its `<dev-base>` baseline, and worlds A, C and D build on its structural moves (task 1.4). Groups 2 to 7 then run in parallel, with two internal orderings: task 6.1 before the rest of group 6, and tasks 7.1 and 7.2 before the rest of group 7. Group 8 starts when groups 2 to 7 have handed over, then 9, then 10.

Rules for every group:
- Every phone rule sits inside the gate that design D2 names for it; a phone-only element is created by script under that gate (design D3).
- Until group 9 is done, a production build prints one `[museum]` staleness line per loop. That is not a failure before then.
- Only the integrator commits (groups 8, 9 and 10): Conventional Commits `type(scope): subject`, with no co-author or tool trailer. Nobody deploys or pushes.
- No file under `sites/4d-os/public/packs/` or `sites/playground/public/og/` changes, and `package.json` does not change.
